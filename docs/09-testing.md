# الاختبارات

## الفلسفة

الاختبارات تُشغَّل على قاعدة بيانات حقيقية، لا على محاكاة. كل ملف اختبار خلفي
يجري داخل **معاملة واحدة تنتهي بـ `RAISE EXCEPTION` متعمَّد**، فتُلغى المعاملة
بالكامل ولا يبقى أي أثر — ولا حتى في سجل التدقيق (وهو سجل لا يُحذف عادةً).
التقرير يصل عبر نص الاستثناء نفسه.

## لماذا لا يوجد `pg_sleep`؟

`now()` ثابتة داخل المعاملة الواحدة، ولا يمكن تسريع الوقت. البديل الشائع هو
حقن "ساعة قابلة للتزوير" في كود الإنتاج — وقد رُفض عمدًا: **إضافة باب خلفي
للتحكم في الوقت داخل نظام مهمته الأولى منع التلاعب بالوقت مخاطرة غير مقبولة**،
حتى لو كان محميًا.

البديل المُعتمد: تُحاكى المدد بتأريخ **الحالة المخزَّنة** إلى الوراء مباشرةً
(`last_interaction_at`, `marked_until`, `started_at`). هذا مكافئ تمامًا لمرور
الوقت من وجهة نظر المحرك، ويجعل النتائج قطعية ولا تعتمد على انتظار حقيقي.

## التشغيل

### اختبارات الخلفية (SQL)

```bash
# عبر Supabase CLI
supabase db execute -f tests/01_attendance_activity_engine.sql
supabase db execute -f tests/02_security_and_integrity.sql
```

أو لصق محتوى كل ملف في **SQL Editor**. النجاح يظهر كـ"خطأ" يحمل التقرير — وهذا
مقصود: هو ما يضمن التراجع الكامل.

يحتاج كل ملف حسابين على الأقل في `auth.users` غير مرتبطين بموظفين (يُختاران
تلقائيًا). لا يُنشئ الاختبار أي حساب جديد ولا يعدّل أي حساب قائم.

### اختبار عرض الواجهات

```bash
npm i playwright-core
python3 -m http.server 8899 &
node tests/ui-smoke.mjs
```

يستبدل عميل Supabase بعميل وهمي **داخل المتصفح أثناء الاختبار فقط** ليتحقق أن
كل صفحة تُرسم بلا خطأ JavaScript، وأن الجداول والبطاقات تتعامل مع الصفوف
الفارغة والكاملة، وأن الواجهة عربية بالكامل. لا علاقة لهذا بتشغيل النظام.

## ما جرى اختباره فعليًا

### `01_attendance_activity_engine.sql` — ٢٤ حالة

| # | ما تتحقق منه |
|---|---|
| ت١ | الحالة الابتدائية "لم يبدأ العمل" |
| ت٢ | بدء الشيفت ينشئ جلسة مفتوحة واحدة بوقت الخادم |
| ت٣ | رفض شيفت ثانٍ (EO001) |
| ت٤ | النبضة الأولى لا تمنح وقتًا وهميًا |
| ت٥ | حفظ حدث معروف ورفض نوع مجهول |
| ت٦ | بعد ٣٠ دقيقة بلا تفاعل: يُحتسب ٣٠٠ ثانية فقط (عتبة الخمول) |
| ت٧ | كشف الخمول تلقائيًا |
| ت٨ | **تفاعل بعد ٢٥ دقيقة خمول لا يمنح أي وقت رجعي** |
| ت٩ | **جهازان متزامنان: الأول يُحتسب والثاني صفر** |
| ت١٠ | ٣ جلسات نشاط لكن جهازان مميزان فقط |
| ت١١ | رفض النداء الزائد عن الحد (throttled) |
| ت١٢–١٦ | الاستراحة: البدء، رفض الثانية، عدم احتساب النشاط، الإنهاء، رفض إنهاء غير قائمة |
| ت١٧ | **المعادلة متسقة: نشاط + خمول = شيفت − استراحة** |
| ت١٨ | الخط الزمني يحتوي فترات نشاط وخمول واستراحة محسوبة |
| ت١٩–٢١ | إنهاء الشيفت، رفض الإنهاء المكرر، رفض النشاط خارج الشيفت |
| ت٢٢ | الإحصاءة اليومية = مجموع دقائق النشاط بالضبط |
| ت٢٣ | سجل التدقيق سجّل العمليات الأربع |
| ت٢٤ | الإغلاق التلقائي ينهي الشيفت عند **آخر نبضة** لا عند الآن |

**النتيجة الأخيرة: ٢٤/٢٤ ناجحة.**

> ت١٠ فشل في أول تشغيل وكشف خطأً حقيقيًا: عدّ الأجهزة كان يعدّ صفوف
> `(جهاز × تطبيق مصدر)` بدل الأجهزة المميزة، فيظهر حاسوب واحد يعمل على مدعوم
> وعلى لوحة العمليات وكأنه جهازان. صُحّح في الترحيل `0015`.

## ما لم يُختبر

- **دورة تسجيل دخول حقيقية من المتصفح إلى الخادم**: بيئة التطوير المستخدمة
  تمنع الاتصال الخارجي بنطاق `supabase.co`، فتعذّر تنفيذ اختبار طرف-إلى-طرف
  بمتصفح حقيقي مقابل الخادم الحي. المصادقة نفسها هي Supabase Auth القياسية،
  وكل ما يليها مُختبَر على قاعدة البيانات مباشرةً.
- **التسابق الحقيقي بين اتصالين متوازيين**: مُنع منطقيًا بـ`SELECT … FOR UPDATE`
  على صف الحالة وبالفهارس الفريدة، واختُبر داخل اتصال واحد. اختبار تحميل
  متعدد الاتصالات يستحق الإضافة قبل التوسع إلى مئات الموظفين.
- **حمل حقيقي**: التصميم يحتمل مئات الموظفين نظريًا (طلب واحد/دقيقة/جهاز)،
  لكن لم يُجرَ اختبار حمل فعلي.
