# المعمارية — Mad3oom Employee Operations

> هذه الوثيقة هي المرجع المعماري للنظام. تمت كتابتها **قبل** كتابة أي كود، وتُحدَّث مع كل قرار معماري جديد.

## 1. ما هو النظام

نظام داخلي لإدارة حضور موظفي منصة مدعوم وقياس نشاطهم الفعلي داخل بيئة العمل.
النظام **ليس** أداة مراقبة شخصية: لا يسجّل ضغطات لوحة المفاتيح، ولا يصوّر الشاشة، ولا يتتبّع المواقع
الأخرى، ولا يقرأ محتوى ما يكتبه الموظف. هو يقيس **أحداث عمل معرَّفة مسبقًا** داخل منصة مدعوم فقط.

## 2. المبدأ الحاكم: قاعدة البيانات هي مصدر الحقيقة

كل رقم يظهر في أي واجهة له مصدر واحد: صف في PostgreSQL.
لا يوجد في النظام أي بيانات وهمية، ولا أي إحصائية محسوبة في المتصفح ثم تُخزَّن كحقيقة.

المتصفح **لا يُصدِّق فيه أبدًا** في أي من الآتي:
- الوقت (`started_at` / `ended_at` / `duration`) — كلها من `now()` على الخادم.
- الهوية (من هو الموظف) — من `auth.uid()` داخل الـ JWT الموقَّع، وليس من parameter.
- الصلاحية (هل يحق له تنفيذ العملية) — تُفحص داخل الدالة على الخادم + RLS.

## 3. القرار المعماري الأول: أين تعيش قاعدة البيانات؟

**القرار:** مخطط (schema) مستقل اسمه `emp_ops` داخل نفس مشروع Supabase الخاص بمنصة مدعوم.

**البدائل التي دُرست:**

| البديل | لماذا رُفض / قُبل |
|---|---|
| مشروع Supabase جديد بالكامل | يعني قاعدة مستخدمين ثانية ⇒ الموظف يسجّل دخولًا مرتين، ولا يمكن لمنصة مدعوم أن ترسل أحداث نشاط بهوية الموظف دون مشاركة مفاتيح خدمة بين مشروعين. أمنيًّا وتشغيليًّا أسوأ. |
| جداول داخل `public` بسابقة `eo_` | يلوّث مخطط منصة مدعوم (أكثر من 150 جدولًا بالفعل) ويخلط الحدود بين النظامين. |
| **مخطط `emp_ops` مستقل + نفس Supabase Auth** ✅ | عزل كامل على مستوى المخطط، ولا يُمسّ أي جدول قائم في `public`، مع مشاركة الهوية (`auth.users`) مما يجعل تكامل مدعوم لاحقًا مجرد استدعاء RPC بجلسة الموظف نفسها. |

**نتيجة مهمة:** لم يُعدَّل أي جدول أو دالة أو سياسة قائمة في منصة مدعوم. الاعتماد الوحيد على الخارج هو
مفتاح أجنبي للقراءة على `auth.users(id)`.

## 4. القرار المعماري الثاني: كيف يصل الـ Frontend إلى البيانات؟

**القرار:** الواجهة **لا تملك أي صلاحية كتابة مباشرة على أي جدول**. كل عملية تمرّ عبر دالة
`SECURITY DEFINER` منشورة في مخطط `public` بسابقة `eo_`.

```
Browser ──(JWT)──▶ PostgREST ──▶ public.eo_*(...)  [SECURITY DEFINER]
                                      │
                                      ├─ 1. تحديد الموظف من auth.uid()
                                      ├─ 2. فحص الحالة (active/suspended)
                                      ├─ 3. فحص الصلاحية (rank)
                                      ├─ 4. فحص قواعد سلامة البيانات
                                      ├─ 5. الكتابة بتواريخ الخادم فقط
                                      └─ 6. تسجيل Audit Log
                                            ▼
                                      emp_ops.* (جداول)
```

الصلاحيات على مستوى Postgres:
```sql
REVOKE ALL ON ALL TABLES IN SCHEMA emp_ops FROM anon, authenticated;
GRANT SELECT ON <جداول القراءة> TO authenticated;  -- محكومة بـ RLS
-- لا يوجد INSERT / UPDATE / DELETE لأي دور عميل، على أي جدول، إطلاقًا.
```

هذا يعني أن الموظف حتى لو عدّل JavaScript في المتصفح، أو استدعى REST API مباشرة بمفتاحه، لا يستطيع
كتابة صف واحد إلا عبر دالة تفحصه.

**لماذا `public.eo_*` وليس `emp_ops.*` للدوال؟** لأن PostgREST لا يعرض إلا المخططات المُعلَنة في إعدادات
المشروع (`public`, `graphql_public`). نشر الدوال في `public` يجعل النظام يعمل **دون أي تغيير في إعدادات
المشروع** ودون المخاطرة بتعديل سطح الـ API الخاص بمنصة مدعوم. الجداول تبقى في `emp_ops` غير مكشوفة عبر REST
أصلًا — طبقة حماية إضافية.

الجداول رغم ذلك تحمل سياسات RLS كاملة (قراءة) لسببين: الدفاع في العمق، ولأن Supabase Realtime يفحص RLS
مباشرة على الجدول (لا يمرّ عبر PostgREST).

## 6. آلة الحالة (State Machine)

حالة الموظف **ليست عمودًا يكتبه العميل**؛ هي **دالة محسوبة** من وقائع مخزَّنة:

الوقائع: (١) هل توجد جلسة حضور مفتوحة؟ (٢) هل توجد استراحة مفتوحة؟ (٣) متى آخر تفاعل حقيقي؟
(٤) متى آخر نبضة؟

```
                 لا توجد جلسة حضور مفتوحة اليوم
                              │
                         NOT_STARTED  (لم يبدأ العمل)
                              │ eo_start_shift
                              ▼
                          WORKING ──────────────┐
                              │                  │ eo_start_break
              آخر تفاعل ≤ عتبة الخمول            ▼
                              │                BREAK (في استراحة)
                              ▼                  │ eo_end_break
                           ACTIVE  ◀─────────────┘
                              │ مرور عتبة الخمول بلا تفاعل
                              ▼
                            IDLE
                              │ أي تفاعل حقيقي
                              └──▶ ACTIVE
                              │
              آخر نبضة > عتبة الانقطاع (مع بقاء الشيفت مفتوحًا)
                              ▼
                       DISCONNECTED (غير متصل)
                              │ eo_end_shift  أو  إغلاق تلقائي
                              ▼
                           OFFLINE
```

الترتيب في الحساب (أول شرط يتحقق يفوز):
`NOT_STARTED → BREAK → DISCONNECTED → IDLE → ACTIVE`

الحالة كلها تُشتق في دالة واحدة: `emp_ops.compute_presence(...)`. لا توجد شروط حالة متناثرة في الملفات.

## 7. لماذا "دقائق النشاط" وليس "مجموع المدد"

المشكلة الكلاسيكية: ثلاثة تبويبات مفتوحة ⇒ ثلاث ساعات نشاط لساعة واحدة حقيقية.

الحل المُعتمد: جدول `activity_minutes` مفتاحه الأساسي `(employee_id, minute_start)`.
كل تبويب أو جهاز يبلّغ عن نشاطه، والكتابة `ON CONFLICT DO UPDATE` ⇒ الدقيقة الواحدة تُحسب مرة واحدة
مهما بلّغ عنها عشرة تبويبات. **الاتحاد (Union) يحدث في المفتاح الأساسي نفسه، لا في كود التجميع.**

`Active Time = COUNT(دقائق) × 60 ثانية` — رقم قابل للتفسير والتدقيق دقيقة بدقيقة.

التفاصيل الكاملة في [`05-activity-logic.md`](./05-activity-logic.md).

## 8. الخصوصية بالتصميم

ما يُخزَّن: نوع الحدث (من كتالوج معرَّف)، وقت الخادم، معرّف الكيان (رقم تذكرة مثلًا)، معرّف جهاز
مجهول (UUID عشوائي في `localStorage`)، اسم المتصفح/النظام مختصرًا.

ما **لا** يُخزَّن أبدًا: نص المفاتيح، محتوى الحقول، لقطات شاشة، إحداثيات الفأرة، أي نشاط خارج نطاق
مدعوم. عنوان الـ IP يُخزَّن على مستوى جلسة النشاط فقط (لكشف تعدد الأجهزة والتدقيق الأمني) ولا يُعرض
إلا لمن يملك صلاحية إدارية.

## 9. الوقت والمنطقة الزمنية

- التخزين: `timestamptz` دائمًا (UTC داخليًّا).
- التجميع اليومي: عمود `work_date` يُحسب على الخادم بمنطقة الموظف الزمنية (`employees.timezone`،
  الافتراضي من الإعدادات `Africa/Cairo`) — حتى لا ينقسم شيفت ليلي على يومين خطأً.
- العرض: منطقة النظام من جدول الإعدادات، قابلة للتغيير من صفحة الإعدادات دون لمس الكود.

جلسة Supabase الموجودة أصلًا في المنصة ويستدعي `public.eo_ingest_activity`.
